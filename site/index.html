Project overview

A real integration platform, built to learn the hard parts properly.

Accord is a passion project. It exists to build practical, production-minded depth in the work that sits between systems: calling external APIs, receiving their events, and making sure both sides end up telling the same story.

Rather than a toy demo, it’s designed the way a serious integration service would be, with signature verification, a durable delivery log, idempotent processing and a clear plan for recovery and reconciliation. Every decision is a chance to practice the trade-offs for real.

Skills it’s built to strengthen

  • API integrationsAuthentication, signatures, rate limits and the quirks of each provider.
  • Backend engineeringGo services, PostgreSQL and clean, testable boundaries.
  • Distributed systemsConsistency, ordering and failure between services that share no state.
  • DevOpsContainers, migrations, deployment and the tooling to watch it all run.

Engineering challenges

The request is the easy part. Agreement is the hard part.

Independent systems don’t share memory, clocks or transactions. Accord is a place to work through what it takes to keep them consistent anyway.

1 · Provider Sends an event Stripe today; Plaid, Shippo and Zendesk next.
2 · Accord gateway Verifies and stamps Checks the signature, records received_at in UTC.
3 · Delivery log Records every request One Postgres row per delivery, flagged original, duplicate or rejected.
4 · Planned Workflows and reconciliation Downstream actions, retries and checks against each provider.

Duplicate deliveries

Providers retry. How do you record every copy for an honest audit trail, yet act on each event exactly once, even when two copies race?

Forged and malformed requests

Rejected requests are logged too, sanitized first, and kept out of deduplication so no one can pre-claim a real event ID.

Out-of-order events

An update can arrive before the create it depends on. Ordering has to come from the data, not the arrival time.

Partial failures

The payment succeeded but the shipment call timed out. Recovery means knowing exactly which steps finished and which to retry.

Drift between systems

Even with careful processing, records diverge over time. Reconciliation finds the gaps and makes them visible.

Knowing what happened

When something goes wrong at 2 a.m., the system should explain itself plainly and point to a useful next step.

Design principles

  • Every request is recorded, never silently dropped.
  • Timestamps are stored in UTC, converted at the boundary.
  • Schema lives in migrations; the app only reads and writes.
  • Dependencies are injected so every piece can be tested.
